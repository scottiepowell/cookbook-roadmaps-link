# Local UI Real-Save Wiring

Status: complete for local/dev-only use; production Save-to-Cookbook remains
unimplemented.

Date: 2026-07-26

## What changed

The importer review panel in `ai-api/app/static/demo.js` now chooses between
two deliberately separate paths:

- with the persistent local gates off, it keeps the existing 0033S in-memory
  prototype and clearly labels the result as non-production;
- with every gate on, it calls the sidecar's
  `/adapter/recipes/import-candidate/local-persistent-commit` route, which
  calls the existing 0034G transport and the core-owned disposable route in
  `local/vanilla-cookbook-adapter:0034g`.

The UI always starts with an unsaved draft. The operator reviews the title and
description, runs the existing dry-run, checks the explicit confirmation box,
and then chooses the local/dev-only save control. The response renderer shows
only safe status, UID, canonical local link, idempotency, duplicate/conflict,
rollback, and read-after-write fields.

## Gates and payload boundary

The persistent route is unavailable unless all of the following are true:

- `AI_LOCAL_SAVE_ENABLED=true`;
- `AI_LOCAL_SAVE_APPROVED=true`;
- `AI_LOCAL_COOKBOOK_RUNTIME_VERIFIED=true`;
- `VANILLA_COOKBOOK_IMAGE=local/vanilla-cookbook-adapter:0034g`;
- `COOKBOOK_TARGET_URL` resolves to loopback HTTP on the local Cookbook port;
- the Compose project is `cookbook-local`;
- the request is from a loopback/test client; and
- the process is not in production, CI, AWS, Cloudflare, tunnel, or deployment
  context.

The UI confirmation is sent as `confirm_local_save=true` only on this gated
path. The sidecar sends the reviewed candidate, idempotency key, contract
version generated by the transport, and local approval. It never sends a
`userId`, ownership claim, cookie, session, token, OAuth value, provider grant,
or storage grant. Core owns the synthetic AuthUser and commit authorization.

All gates are disabled by default. The readiness endpoint reports only a
boolean and safe guidance; it does not expose the image marker, target, or
environment values.

## Observation boundary

0034G proved core read-after-write using safe opaque UID/status checks and
restores the disposable database/uploads after verification. The browser UI
does not claim that a real authenticated user can open the saved recipe: no
real session, cookie, token, or browser automation is used. A local core UID
and safe verification status are the strongest supported result here.

## Remaining work

Real Google login, persistent user sessions, normal authenticated sidecar
transport, production Save-to-Cookbook, and a production-safe canonical link
remain future architecture work. The 0034E identity foundation does not
change this boundary, and Google Drive/storage consent remains separate.

0034J recommends pausing further synthetic-save expansion for a core-local
mock OIDC session fixture. Until that session gate passes, this UI remains a
local synthetic transport demonstration and cannot claim browser-observable
ownership of a saved recipe.

## Explicit non-goals

This change adds no production route, production authentication, OAuth/provider
call, migration, direct sidecar DB write, browser/session automation, provider
storage grant, analytics, ads, payment, QMD integration, AWS, Cloudflare,
GitHub Actions, or external source.
